# Agent Docs — 컨텍스트 절약형 범용 에이전트 템플릿

Codex의 `AGENTS.md`에 **최소한의 공통 규칙만** 두고, 세션 상태·작업별 계획·선택적 문서·문서 정리 절차를 필요할 때만 읽도록 하는 템플릿이다. 코드뿐 아니라 조사·문서 작성·데이터·시스템 운영 등에도 적용한다.

## 다섯 가지 핵심 기능

1. **세션 연속성:** 새 세션에서 짧은 현재 작업 인덱스를 확인해 관련 작업만 복원한다.
2. **자율 분할:** 복합 업무의 단계·완료 조건·검증 방법을 에이전트가 만든다.
3. **단계 경계:** 한 번에 주요 단계 하나씩 실행·검증하고 상태를 저장한다.
4. **최종 검증:** 최초 요청과 실제 산출물을 재대조해 통과/실패/미검증을 기록한다.
5. **컨텍스트 절약·자율 정리:** 필요한 문서의 필요한 부분만 읽고, 단계 종료 시 인계 문서와 인덱스를 정리한다.

위 규칙들은 **모델에 주는 지침**이다. 하네스가 이를 독립적으로 강제하는 코드가 아니며, 정해진 시간에 백그라운드에서 파일을 정리하는 스케줄러도 아니다.

## 문서 구성

```text
AGENTS.md                         # Codex가 항상 보는 짧은 행동 원칙
CLAUDE.md                         # Claude Code에서 AGENTS.md 참조
agent-docs/current-status.md      # 매 세션에 읽는 짧은 활성 작업 카드
agent-docs/INDEX.md               # 경로가 모호할 때만 읽는 선택적 문서 인덱스
agent-docs/plans/TEMPLATE.md      # 복합 작업 계획을 새로 작성할 때만
agent-docs/plans/<task-id>.md     # 해당 작업의 상단 재개 카드 + 단계·검증
agent-docs/context-maintenance.md # 정리 집중 점검 때만 보는 프로토콜
agent-docs/decisions.md           # 지속되는 중요한 결정
agent-docs/repository-map.md      # 코드 경계가 모호할 때만 읽는 구조 지도
```

## 일반적인 세션의 조회 순서

1. **기본:** Codex가 `AGENTS.md`를 적용하고, 있으면 `current-status.md`를 확인한다.
2. **연관 작업이 있을 때만:** 계획의 **상단 재개 카드**를 읽는다. 현재 단계 내용이 부족하면 그 섹션만 추가 조회한다.
3. **문서가 필요할 때만:** 알던 경로 → 관련 구간 검색 → 요약·목차 → 본문 필요한 구간 순으로 조회한다. 경로를 모르면 `INDEX.md`를 본다.
4. **실행:** 한 주요 단계를 진행하고 해당 단계의 검증 결과를 기록한다.
5. **인계:** 원래 목적·확인된 사실·근거 위치·미검증 사항·다음 행동을 짧게 저장한다.
6. **필요한 시점에 정리:** 단계마다 가볍게 정리하고, 3개 주요 단계 또는 최종 완료 시 관련 작업 문서만 집중 점검한다.

작업이 단순하다면 계획 문서나 정리 문서를 읽지 않는다. 전체 문서 분석, 법률·보안 검토 등 원문이 필요한 요청이라면 **정확성을 위해 필요한 범위는 모두 읽는다**. 요약은 원본을 대신하지 않는다.

## 문서를 어떻게 보존하고 줄이는가?

| 구분 | 저장 장소 | 원칙 |
| --- | --- | --- |
| 공통 행동 규칙 | `AGENTS.md` | 짧게 유지, 유형별 세부 매뉴얼은 분리 |
| 현재 작업과 다음 행동 | `current-status.md` | 한 화면 분량, 자세한 작업 설명 반복 금지 |
| 단계·완료 조건·검증 | `plans/<task-id>.md` | 재개 카드가 먼저, 완료 단계 기록은 압축 |
| 오래 쓰는 결정 이유 | `decisions.md` | 한 사실 한 위치 |
| 선택적 문서 위치 | `INDEX.md` | 경로·요약·읽을 조건만 |
| 원문·실제 산출물·증빙 | 원본 파일/시스템 | 축약·삭제하지 않고 확인 가능한 위치 연결 |

**예시:** 서버 장애 단계가 끝나면 인계 문서에 로그 1,000줄을 붙이지 않는다. 대신 '설정 오류를 발견했고, 해당 시각의 로그 경로와 줄 범위가 있으며, 해결 후 서비스 상태 검증은 미실시'라고 기록한다. 나중에 다시 필요한 로그 구간만 열어 검증한다.

## 문서 정리 주기

- **매 주요 단계 종료:** 이미 열고 고친 계획·상태 문서에서 낡은 값, 중복, 불필요한 실행 로그를 제거한다.
- **3개 주요 단계마다 / 작업 최종 완료 시:** `context-maintenance.md`를 필요한 경우 읽고 현재 작업과 연결된 문서만 집중 정리한다.
- **즉시 점검:** 활성 상태가 실제 상태와 충돌하거나, 인덱스가 비대해져 문서를 찾기 어려운 경우.
- **정리하지 않는 것:** 원본 자료, 사용자 작성 문서, 계약·감사 자료, 검증 증거, 해결되지 않은 오류·제약.

이 주기는 **에이전트가 실행되는 동안의 단계 기준**이다. 주간/일간 자동 정리를 원한다면 별도의 스케줄러가 필요하다. `AGENTS.md`만으로 백그라운드 작업은 시작되지 않는다.

## 도입 및 확인

1. 작업 공간에 템플릿을 배치한다. 모든 작업 공간에 공통 지침을 적용하려면 Codex의 전역 `~/.codex/AGENTS.md`도 사용할 수 있지만, **작업별 상태와 자료는 해당 공간에 둔다**.
2. 짧은 업무 하나와 3단계 이상인 복합 업무 하나를 진행해 본다.
3. 새 세션에서 `current-status.md`와 관련 계획의 재개 카드만으로 다음 행동을 정확히 시작하는지 확인한다.
4. 긴 문서와 대량 로그를 주고, 필요한 구간만 읽는지 확인한다.
5. 3개 주요 단계 후 불필요한 중복이 정리되고 실패·미검증·검증 근거는 남는지 확인한다.
6. 최초 요청을 기준으로 한 최종 검증과, 실제 토큰 사용량·완료율을 별도로 측정한다.

**관련 연구:** [Lost in the Middle (2024)](https://aclanthology.org/2024.tacl-1.9/) · [Context Length Alone Hurts LLM Performance Despite Perfect Retrieval (2025)](https://aclanthology.org/2025.findings-emnlp.1264/). 이 연구들은 장문 입력의 한계를 보여주지만, 본 템플릿이 특정 Codex 모델의 성능을 어느 정도 높인다는 직접적인 증거는 아니다.
